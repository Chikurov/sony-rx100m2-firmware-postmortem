# WBI1 (раздел nflasha5)

ФАКТЫ по `fw_tar/0700_part_image/dev/nflasha5` (25 619 968 Б).

| Смещение | Значение | Комментарий |

| 0x00 | `"WBI1"` | magic |
| 0x04 | 0xA0 (160) | возможно, размер заголовка |
| 0x08 | 9 | версия? |
| 0x0C | 0x800498E0 | неизвестно |
| 0x10 | 0x20060224 | неизвестно |
| 0x14 | 0x200 (512) | размер блока? |

## Содержимое

- 0xA0…0x1FF — нули; с 0x200 — `0xFF` (стёртая область).
- Данные начинаются примерно с 0x100000.
- Энтропия по файлу ≈ 6.9; 10% нулей, 1.3% `0xFF`.
- Найденные сигнатуры `cramfs`/`ELF` — ложные совпадения внутри данных.

## Драйвер WBI в ядре (ФАКТ)

В `vmlinux.bin` есть символы `wbi_send_sections`, `wbi_compress`, `wbi_exec`,
`wbi_send_data`, `wbi_tsk_init`, `__wbi_drop`, `wbimem=`.

Функция `FUN_c002c440` (ядро, база `0xC0008000`) разбирает поток команд:

- байты `0x00..0x3F` / `0x40..0x7F` — переходы/смещения;
- `0x80` — маска регистров, `0x90..0x9F` — выбор регистра;
- `0xA0` — загрузка 4–11 значений;
- `0xB0` — конец блока, `0xB1` — маска, `0xB2` — пропуск;
- проверки `0x80000000`/`0x81000000` в заголовках секций.

Это **байткод-интерпретатор**, а не простой формат файла. Похоже, раздел
`nflasha5` содержит данные/программу для него.

## Декомпрессор: детали (ФАКТ)

- `FUN_c002c3d0` — побитовый читатель: `struct { char *buf; ...; int size; int bitpos; }`,
  читает байты MSB-first и хранит позицию в битах.
- `FUN_c002c350` — бинарный поиск по таблице секций (адрес/длина).
- `FUN_c002c440` — интерпретатор потока: опкоды `0x00–0x3F`,
  `0x40–0x7F`, `0x80` (маска регистров), `0x90–0x9F` (регистр),
  `0xA0` (загрузка 4–11 значений), `0xB0` (конец), `0xB1` (маска),
  `0xB2` (пропуск); регистры — массив `aiStack_6c` (словарь/состояние).

То есть WBI — это **битовый LZ/словарный формат**, а не «VM команд».
Строка `WBI1~` в ядре — отладочный тег рядом с этим кодом.

## Updater: `ud_wbi_drop.elf` (ФАКТ)

В теле апдейтера есть отдельная утилита `ud_wbi_drop.elf` (6 032 Б).
Её строки:

- `Usage: ud_wbi_drop.elf filename`
- `[UD_WBI_DROP] AnalyzePartitionSettingFile() error`
- `[UD_WBI_DROP] wbi size is zero. skip wbi_drop()`
- `[UD_WBI_DROP] error : wbi size is too small. size = $d`
- `[UD_WBI_DROP] %s wbi_drop`
- `[UD_WBI_DROP] wbi_drop() error`

То есть при обновлении раздел WBI **стирается** («drop»), если его размер
из `partinf.conf` больше нуля; при нуле — пропускается.

## `upm.ko` и WBI/DFS (ФАКТ)

- `upm_senser_wbi_drop(struct)` вызывает `wbi_drop()` и упаковывает
  результат (4 байта) в поля структуры — это обёртка статуса, не разбор
  содержимого WBI.
- `k_dfs_do_full_nand()` берёт семафор и вызывает
  `onenand_set_dfs_mode(0)` — DFS отключается на время полной операции
  с NAND.

## `liro.ko` и WBI (ФАКТ + гипотеза)

Строки `liro.ko`: `[LIRO]: liro resume`, `[LIRO]: liro resume (WBI)`,
`liro resume error ...`, `LIRO: resume error(kthread_suspend)`,
`bind task_resume to cpu%d`, `wait for liroapp resume`.
Символы: `liro_resume`, `liro_suspend`, `thread_resume`, `proc_suspend`.

То есть WBI фигурирует в **пути выхода из сна/возобновления**, а не в
файловом формате. Гипотеза: WBI = «Wakeup By Interrupt» (или подобный
источник пробуждения), а раздел `nflasha5` — служебный для этого
механизма. Требует подтверждения.

## Статус

Семантика полей и формат данных — **НЕ РАЗОБРАНЫ**. Раздел помечен в
`partinf.conf` как «WBI(reserved)», практической ценности пока нет.
