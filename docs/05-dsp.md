# DSP / camera firmware `av-cam.bin`

ФАКТЫ по `systemfs/av-cam.bin` (6 451 592 Б).

## Формат

- Сырой ARM-код (не ELF). Первое слово `0xE28FF028` — `add pc, pc, #0x28`
  (таблица переходов), по смещению 4 — ASCII `ORIL`.
- Внутри — RTOS: строки `[CDIAG][TSK]`, `osal_*`, `TskAvifEvent`,
  `LiroSequencer`, `AVFINAL`.
- Есть отладочные строки-сигнатуры C++: `Camera::HAPI::…`,
  `Camera::YC::…`, `Camera::Capture::…`.

## Эффекты (строки-факты)

`Camera::HAPI::Start_Art_Effect(Camera::HAPI::PRM_REQ_FILTER_ART_EFFECT *, …)`,
`PRM_REQ_FILTER_MINIATURE`, `PRM_REQ_FILTER_SOFT_FOCUS`,
`PRM_REQ_FILTER_RICHTONE_MONOCHROME`, `PRM_REQ_FILTER_HDR`,
`PRM_REQ_FILTER_SUPER_RESOLUTION`, `PRM_REQ_FILTER_FACE_NR`,
`PRM_REQ_FILTER_ADDITION_NR`, `PRM_REQ_FILTER_CONTRAST_PLUS`,
`PRM_REQ_FILTER_DEVELOP`, `Start_Miniature`, `Miniature_Main`.

## Таблица параметров (0x5C4278 … 0x5C4804)

Записи по **12 байт**:

```
u32 size (2 или 4);  u32 dsp_addr (0x010C0000 + смещение);  u32 param_id
```

118 записей, ID от `0x1F0` до `0x340`. Адреса идут подряд
(`0x010C00E8`, `0x010C00E9`, …) — это окно параметров в RAM DSP.

Параметры фильтров:

| ID | size | dsp_addr |
|---|---|---|
| 0x2B0 | 4 | 0x010C012C |
| 0x2B4 | 4 | 0x010C012D |
| 0x2B8 | 4 | 0x010C012E |
| 0x2BC | 4 | 0x010C012F |
| 0x2C0 | 4 | 0x010C0130 |
| 0x2C4 | 4 | 0x010C0131 |
| 0x2C8 | 4 | 0x010C0132 |
| 0x2CC | 4 | 0x010C0133 |
| 0x32C | 2 | 0x010C0155 |

Конец таблицы: `FFFFFFFF 00000000 FFFFFFFF 00000000`, далее строки.
Прямых ссылок на эти адреса в коде не найдено — доступ идёт через
общий механизм параметров, а не литералами.

## База загрузки — 0xC3440000 (подтверждено)

Адреса из таблицы перед строками (`0xC3920629`, `0xC392064D`,
`0xC3920787`) — **Thumb-указатели** (нечётные). При базе `0xC3440000`
они указывают на код:

| Адрес | Смещение | Содержимое |
|---|---|---|
| 0xC3920629 | 0x4E0629 | Thumb, `bx lr` рядом |
| 0xC392064D | 0x4E064D | Thumb, `bx lr` рядом |
| 0xC3920787 | 0x4E0787 | Thumb, `pop {r3,pc}` |

Ghidra с базой `0xC3440000` декомпилировала функцию
`FUN_c392061c`: `if (param_2==0) *(u32*)(p+0x10) &= ~4; else |= 4;`
— осмысленный код, база подтверждена.

Адреса из заголовка (`0xC3441050`, `0xC3441078`, …) при этой базе
попадают в начало кода (0x1050, 0x1078) — тоже согласуется.

## Карта кода (Ghidra, база 0xC3440000)

- Функций: **23 088**, суммарный размер тела ≈ 2,77 МБ (из 6,45 МБ файла).
- Медианный размер 44 Б, максимальный 9 288 Б.
- Крупнейшие: `0xC3719824` (9288), `0xC36AE0D2` (6960), `0xC34DD5D0` (5812),
  `0xC3674586` (5630), `0xC34DED94` (4920).
- Полная карта: `ghidra_out/avcam_funcs.tsv` (адрес, размер, имя).
- Декомпилированы 15 крупнейших функций (`ghidra_out/top_funcs/`).
  Прямых обращений к окну `0x010C0000` в них нет (совпадение `0x10c`
  оказалось индексом массива, не адресом).

## Таблица трассировки (0x4F7B4C и далее)

Найдена структура:

```
u32 trace_addr; u32 0; char signature[]; ...
```

Примеры: `0xC392064D` → `void Camera::HAPI::Start_CreateStream(...)`,
`0xC3920787` → `void Camera::HAPI::Start_Art_Effect(...)`.

Адреса указывают **внутрь** функций (точки вызова/трассировки), а не на
их начало — поэтому Ghidra не строит там функции. Это объясняет,
почему прямых ссылок на строки нет.

## `Start_Art_Effect`: обёртка (0xC392077C)

По точке трассировки найдена содержащая функция `FUN_c392077c`
(смещение 0x4E077C). Разбор вручную:

```
push {r3, lr}
ldr  r2, [pc, #16]   ; 0xC391A5CD — Thumb-указатель (callback)
str  r2, [sp, #0]    ; 5-й аргумент
ldr  r1, [pc, #16]   ; 0xC3C7FED8 — адрес в RAM (вне файла)
movs r2, #1
movs r3, #0x20
bl   <планировщик>
pop  {r3, pc}
```

Вывод: `Start_Art_Effect` не считает фильтр, а **ставит асинхронный
запрос** с указателем на структуру в RAM (`0xC3C7FED8`) и callback
`0xC391A5CD`. Параметры эффекта приходят в эту RAM-структуру извне
(вероятно, через окно параметров `0x010C0000+`).

## Цепочка Start_Art_Effect (найдена)

```
Start_Art_Effect (0xC392077C)
  → планировщик 0xC3915CE0
      args: r0=объект, r1=0xC3C7FED8 (RAM), r2=1, r3=0x20,
            stack[0]=callback 0xC391A5CD
  → callback 0xC391A5CC  ← обработчик эффекта
```

Callback (Thumb, 0xC391A5CC): проверяет `byte[r7+0x1C] == 1`, затем вызывает:

| Вызов | Назначение (не подтверждено) |
|---|---|
| `0xC391A93C` | подготовка |
| `0xC3791D2E`, `0xC3791DD2` | копирование/установка параметров |
| `0xC384184E`, `0xC384196A` | блок изображения |
| `0xC3791EC2`, `0xC3792024`, `0xC3792140` | обработка |
| `0xC391A804` | вспомогательная |
| `0xC3841A6A` | завершение |

Это уже реальный код обработки эффекта — следующая точка входа
для трассировки: `0xC3791D2E` и `0xC384184E`.

## Характер обработчика (вывод)

Подфункции `0xC3791D2E`, `0xC384184E`, `0xC3792024`, `0xC384196A` —
типовые помощники обработки изображения: копируют поля структуры
(`ldrh [r0]`, `[r0+2]`, `[r0+4]`), проверяют флаги (`byte[r0+0xC0+0x14]`),
вызывают общие подпрограммы (`0xC36F7414`, `0xC36ECE F6`).

Признаков статических таблиц «рецептов» нет: обработчик читает значения
из структуры, переданной в RAM (`0xC3C7FED8`). То есть параметры эффекта
**формируются во время работы** (хост → окно `0x010C0000+` → структура),
а не лежат готовыми таблицами в файле.

Это объясняет, почему поиск «рецептов» в образе не даёт результата.

## Структура параметров эффекта (наблюдения)

Обработчик `0xC391A5CC` читает поля из двух структур:

- `r7 = r0 + r1` — параметрический блок; используется `[r7+0x1C]`
  (флаг режима), `[r7+0x14]`, `[r7+0x18]`;
- `r6 = r4 + 0x20` — блок состояния; `[r6+8]`, `[r6+0xC]`, `[r6+0xD]`,
  `[r6+0x20]`;
- `r5 = r4 + 0xC0` — блок флагов; `[r5+0x14]`, `[r5+0x18]`.

Значения этих полей формируются во время работы (хост → параметры),
поэтому «рецепт» конкретного вида (Toy/Watercolor/…) в файле не лежит.

Стадии пайплайна — общие модули: `0xC36F7414`, `0xC3650154`,
`0xC36F9248`, `0xC383CEB4`, `0xC3593F90`, плюс глобальные состояния
`0xC3A75xxx` и `0xC3C7Bxxx` (RAM, вне образа).

## Общие модули пайплайна (роли — ПРЕДПОЛОЖЕНИЕ)

| Адрес | Наблюдения | Вероятная роль |
|---|---|---|
| `0xC36F7414` | 26 `ldr`, 25 `strb`, 13 `strh`; вызовы `0xC37E92xx` | доступ к параметрам изображения |
| `0xC3650154` | 30 `cmp`, 19 `bne`; вызовы `0xC3652E2E`, `0xC3650558` | проверка/ожидание состояния |
| `0xC36F9248` | 28 `b`, сдвиги/вычитания, без вызовов | битовые операции/циклы |
| `0xC383CEB4` | `ldrh`/`str`, вызовы `0xC36F5C70`, `0xC36ECE78` | работа с блоками (копирование/конверсия) |
| `0xC3593F90` | 33 `str`, 32 `ldr`; вызовы `0xC36ECE F6`, `0xC3593F74` | копирование/заполнение памяти |

Имена функций в образе отсутствуют (строки — только отладочные
сигнатуры), поэтому роли определены по составу инструкций и вызовам и
помечены как предположения.

## Уточнение: callback — это продолжение, а не функция

Адрес `0xC391A5CD` (нечётный, Thumb) указывает **внутрь** функции, которая
начинается с `0xC391A5A8` (`push {r0,r1,r2,r4,r5,r6,r7,lr}`). То есть
планировщику передаётся адрес продолжения, а не точка входа.

Из-за этого Ghidra не строит там функцию и падает в `halt_baddata`.
Правильный вход — `0xC391A5A8`; при декомпиляции с него Ghidra всё равно
ошибается, вероятно из-за уже записанного в проект «плохого» кода.

## Обработчик эффекта: псевдокод (ФАКТ, Ghidra + принудительный Thumb)

`FUN_c391a5a8(param_1, param_2, param_3)` — состояние изображения,
контекст, аргумент.

```
FUN_c391a290(param_1, param_2)                  ; инициализация
log(1, 0xc, 0x28, ...)
if (ctx[0x281C] == 1) {
    log(1, 0xc, 0x2f, ...)
    func_0xc391a93c(param_1, ctx)
    if (param_1[0x28] == 1) { param_1[1]=ctx[0x2818]; param_1[0]=ctx[0x2814]; }
    func_0xc3791d2e(param_1)
    FUN_c3791dd2(param_1, ctx)
    if (param_1[0xD4] == 0) func_0xc391a804(param_1, param_1+0xBC, ctx)
    else { param_1[3]=param_1[0x30]; param_1[2]=param_1[0x2F]; }
    FUN_c384184e(param_1, param_1+8, byte[0x69], byte[0x6A])
    func_0xc384196a(param_1, ctx)
    FUN_c3791ec2(param_1, param_1[4], param_1[5], ctx)
    FUN_c3792024(param_1, param_1[4], param_1[5])
    func_0xc3792140(param_1)
    if (param_1[0x2C] != 0) { ... очистка флага в списке ... }
    func_0xc3841a6a(param_1)
}
if ((param_1[0x130] & 1) && param_1[0x40] && !param_1[0x2C])
    func_0xc391a43c(param_1, ctx)
```

В конце — запись шести «регистров» через `FUN_c375442e` с кодами
`0x30`, `0x33`, `0x34`, `0x35`, `0x36`, `0x37`; значения собираются из
16-битных полей структуры (`0x2E/0x32`, `0x26/0x1A`, `0x2814/0x2818`,
`0x2B/0x2C`, `0x2D/0x2E`). Похоже на передачу геометрии/параметров в
аппаратный блок (ПРЕДПОЛОЖЕНИЕ).

## Проверка ссылок (база 0xC3440000)

Ghidra-скрипт искал ссылки на:
`0xC3938CAC` (строка `void Camera::HAPI::Start_Art_Effect…`),
`0xC3938CBF` (`Start_Art_Effect`),
`0xC3A04278` (таблица параметров).

Результат: **ссылок 0**. Строки и таблица не адресуются абсолютными
указателями — вероятно, доступ идёт по индексу/смещению либо строки
лежат в отладочной секции без ссылок.
