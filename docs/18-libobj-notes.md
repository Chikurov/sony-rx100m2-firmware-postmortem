# `libObj.so`: заметки для продолжения разбора

16,4 МБ, ELF32 ARM EABI4, stripped (есть только `.dynsym`).

## Важно: база Ghidra

Ghidra грузит библиотеку с **image base `0x10000`**, а не 0. Поэтому
адрес строки из файла `0xD4E9A8` в Ghidra — `0xD5E9A8`. Первые попытки
искать ссылки по файловому адресу давали 0 попаданий именно из-за этого.

## UXC

- Строка `LayoutGroupManager::openLayout(): LayoutConveter and uxc is
  not match` — файл `0xD4E9A8`.
- Ссылка одна: функция `FUN_002f277c` (Ghidra-адрес `0x2F277C`).
- Она вызывает методы переданного объекта-конвертера: `vtable+0xC`
  (получить размер/версию) и `vtable+0x10` (тип), затем создаёт объект
  через `FUN_002f428e`.
- Значит **парсинг UXC — в реализации конвертера**, а не в `openLayout`.
- Экспортированы только геттеры `ux::wgtlay::LayoutConverter::get*`
  (многие — заглушки, возвращают 0) и `BaseConverter::getValue`
  (поиск по ключу в списке).
- `LayoutGroupConverter` экспортирует только деструктор; vtables не
  экспортированы, поэтому класс-наследник нужно искать по фабрикам
  (`LayoutGroupConverter* (*)()` в `WidgetLayouter::openFirst/…`).

## RTTI-скан: что выяснилось (ФАКТ)

- В `.dynsym` только **12** определённых `_ZTI*` (остальные — импорт,
  адрес 0).
- Прямых ссылок на эти typeinfo в `.data` **нет** (0 совпадений).
- Адреса виртуальных заглушек (`0x49F535`, `0x49F555`, `0x49F569`)
  встречаются только в `.dynsym`, но не в таблицах `.data`.
- Значит vtables в файле не лежат готовыми: они заполняются
  релокациями при загрузке (или лежат в области, где в файле нули).

**Следствие:** для восстановления vtables нужен загрузчик ELF с
применением `.rel.dyn` (или динамический анализ), а не поиск по файлу.


## Релокации применены (частичный прогресс)

Скрипт `tools/reloc_apply.py` применил **13 416** релокаций
(`RELATIVE`, `ABS32`, `GLOB_DAT`, `JUMP_SLOT`) к копии `libObj.so`.

После этого в `.data` нашлись ссылки на typeinfo: **106**, из них
**13 таблиц** содержат `_ZTIN2ux6wgtlay15LayoutConverterE` (0xF5BBC0):
`0xF5914C`, `0xF59494`, `0xF597E8`, `0xF59C20`, `0xF5A7E0`, `0xF5AF14`,
`0xF5B0DC`, `0xF5B10C`, `0xF5B190`, `0xF5B1D0`, `0xF5B278`, `0xFA7508`
и одна в начале.

Адреса методов в этих таблицах разрешаются в функции сгенерированных
классов (`ACT_*::cast`), то есть это vtables наследников
`LayoutConverter`. Точная раскладка (`offset_to_top` / typeinfo /
методы) требует проверки: слово перед typeinfo — адрес функции, а не 0.

Следующий шаг: взять таблицу, соответствующую конвертеру из
`openLayout`, и сопоставить `vtable+0xC`/`+0x10` с методами.
